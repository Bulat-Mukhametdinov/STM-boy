# AGENTS.md

## Project Overview

This is an STM32CubeMX-generated embedded C/C++ firmware project for an STM32F4 target.

The current application is `RetroPort`: a small LVGL-driven handheld firmware with a main menu, an emulator catalog
containing CHIP-8, SUPER-CHIP, and an experimental ZX Spectrum 48K core, USB CDC ROM-pack upload, persistent settings in external flash, and simple PWM audio.

| Item                       | Value                                            |
|----------------------------|--------------------------------------------------|
| Project name               | `stm32-proj`                                     |
| Product/UI name            | `RetroPort`                                      |
| MCU                        | `STM32F411CEUx`                                  |
| MCU family                 | `STM32F4`                                        |
| Package                    | `UFQFPN48`                                       |
| Toolchain                  | `arm-none-eabi-gcc`                              |
| Build system               | `CMake` with `Ninja` presets                     |
| Linker script              | `STM32F411XX_FLASH.ld`                           |
| CubeMX file                | `stm32-proj.ioc`                                 |
| STM32CubeMX version        | `6.17.0`                                         |
| STM32Cube firmware package | `STM32Cube FW_F4 V1.28.3`                        |
| UI library                 | `LVGL v9.5.0` via CMake `FetchContent`           |
| Display driver             | Custom HAL ST7735S SPI driver                    |
| Emulator                   | CHIP-8 interpreter with `64x32` framebuffer      |
| External storage           | `W25Q128` SPI flash                              |
| USB device class           | USB FS CDC for ROM-pack upload                   |
| Audio                      | TIM1 PWM output mixed from TIM5 sample interrupt |

## Build Commands

Configure and build the debug firmware:

```sh
cmake --preset Debug
cmake --build --preset Debug
```

Configure and build the release firmware:

```sh
cmake --preset Release
cmake --build --preset Release
```

Expected output artifacts are generated under:

```text
build/Debug/
build/Release/
```

The firmware executable uses the `.elf` suffix. Post-build commands also generate `.bin` and `.hex` next to the `.elf`.

When flashing through STM32CubeProgrammer or ST-Link tooling, prefer the generated `.hex`. If flashing `.bin`, the
address must be:

```text
0x08000000
```

For this project, assume the correct generated artifact is flashed when the user is debugging display behavior. Do not
use "wrong/stale flashed artifact" as a root-cause hypothesis unless the user explicitly asks to audit flashing.

Build a ROM pack from the checked-in ROM collection:

```sh
python3 tools/pack_rompack.py roms -o build/rompack.bin
```

Build and upload the ROM pack over USB CDC:

```sh
python3 tools/pack_rompack.py roms -o build/rompack.bin --upload
```

Upload an existing ROM-pack image:

```sh
python3 tools/flash_rompack_usb.py build/rompack.bin
```

The uploader defaults to the newest `/dev/cu.usbmodem*` or `/dev/cu.usbserial*` port unless `--port` is provided.

## Generated Code Rules

STM32CubeMX owns a large part of this project. Do not casually rewrite generated sections.

When editing generated files, put custom code inside the matching `USER CODE` blocks:

```c
/* USER CODE BEGIN ... */

/* USER CODE END ... */
```

This matters especially in:

| File                           | Notes                                    |
|--------------------------------|------------------------------------------|
| `Core/Src/main.cpp`            | Main entry point, clock setup, main loop |
| `Core/Inc/main.h`              | Shared application declarations          |
| `Core/Src/stm32f4xx_it.c`      | Interrupt handlers                       |
| `Core/Src/stm32f4xx_hal_msp.c` | HAL MSP initialization hooks             |

Avoid editing HAL/CMSIS vendor files unless the change is explicitly about vendor integration or a confirmed upstream
issue.

## Current Hardware Configuration

The authoritative pin assignment lives in `Core/Inc/board_pins.h` and in the repository-level
[docs/pinout.md](../../docs/pinout.md). Read them before changing GPIO, SPI, display, flash, button, joystick, or audio
wiring. Do not infer pins from older Arduino sketches or stale notes.

Current manually confirmed buses:

| Device          | Bus    | Pins                                                                |
|-----------------|--------|---------------------------------------------------------------------|
| ST7735S display | `SPI1` | `SCK=PA5`, `MOSI=PA7`, `CS=PA4`, `DC=PB0`, `RST=PB1`, `BLK=PA6`     |
| W25Q128 flash   | `SPI3` | `SCK=PB3`, `MISO=PB4`, `MOSI=PB5`, `CS=PA15`                        |
| PAM8302 audio   | PWM    | `AUDIO_PWM=PA8`, `AMP_SD=PB2`                                       |
| USB FS CDC      | USB FS | `VBUS=PA9`, `DM=PA11`, `DP=PA12`                                    |
| Power status    | GPIO   | `BAT_STAT=PA1`, `CHRG_STAT=PA0`, `OFF_REQ=PA2`, `OFF_ACK=PA3`       |

`BAT_STAT` and `CHRG_STAT` are swapped on the v0.1 board relative to the original schematic notes. The assignment above
is the one verified on hardware: shorting `CHRG_STAT` pulled the battery ADC to zero. `BAT_STAT` is `ADC1_IN1`.

Current active-low controls:

| Control | STM32 pin |
|---------|-----------|
| A       | `PB13`    |
| B       | `PB14`    |
| X       | `PB12`    |
| Y       | `PB15`    |
| Up      | `PB9`     |
| Left    | `PB7`     |
| Right   | `PB6`     |
| Center  | `PA10`    |
| Down    | `PB8`     |

Physical layout of the action buttons, for on-screen hints and UI mockups: `Y` top, `B` right, `A` bottom, `X` left.

Display notes:

| Item                        | Value                                                                  |
|-----------------------------|------------------------------------------------------------------------|
| Resolution used by firmware | `160x128` landscape                                                    |
| Controller                  | `ST7735S`                                                              |
| Backlight                   | `PA6`, active-high                                                     |
| LVGL color mode             | RGB565 with byte swap enabled                                          |
| ST7735 MADCTL               | `0xA0`, matching landscape rotation used in the working Arduino sketch |

The `.ioc` configuration contains a minimal setup:

| Peripheral | Configuration                                                                        |
|------------|--------------------------------------------------------------------------------------|
| `SYS`      | `SysTick` enabled                                                                    |
| `RCC`      | HSI baseline in the `.ioc`; overridden in code                                       |
| `NVIC`     | Core exception handlers configured                                                   |
| GPIO       | No user GPIO pins configured in `.ioc`; app GPIO/SPI/timers are initialized manually |
| USB        | USB CDC stack is linked manually; `rom_upload.c` starts/stops the device runtime     |

The runtime clock tree is configured in `Core/Src/main.cpp`, not by the `.ioc` baseline. It runs from the external
8 MHz crystal so USB has an exact 48 MHz clock:

| Clock    |    Value | Source                                        |
|----------|---------:|-----------------------------------------------|
| `SYSCLK` | `96 MHz` | HSE 8 MHz, `PLLM=4`, `PLLN=192`, `PLLP=4`     |
| `HCLK`   | `96 MHz` | `AHB = SYSCLK / 1`                            |
| `APB1`   | `48 MHz` | `APB1 = HCLK / 2`                             |
| `APB2`   | `96 MHz` | `APB2 = HCLK / 1`                             |
| `USB`    | `48 MHz` | `PLLQ=8`                                      |

Peripheral timing derived from these clocks (audio sample timer, SPI prescalers, ADC prescaler) must be rechecked if
the clock tree changes.

## Display And LVGL Notes

The firmware uses LVGL for the RetroPort shell UI. `Core/Src/display.c` initializes ST7735 first, then LVGL, then
registers a partial render buffer.

| Item         | Value                                                  |
|--------------|--------------------------------------------------------|
| Draw buffer  | `DISPLAY_HOR_RES * DISPLAY_BUFFER_LINES` RGB565 pixels |
| Buffer lines | `20`                                                   |
| LVGL tick    | `lv_tick_inc(1)` is called from `SysTick_Handler()`    |
| Flush path   | LVGL flush callback calls `ST7735_WritePixels()`       |

Do not leave temporary display diagnostics in normal firmware. In particular, remove color bars, forced delays before
LVGL, GPIO pin scanners, and startup assembly GPIO hacks after debugging.

The custom ST7735 driver currently uses an Adafruit-like black-tab init sequence (`FRMCTR`, `PWCTR`, `VMCTR`, gamma
tables, `INVOFF`, `NORON`, `DISPON`) and `SPI_DIRECTION_2LINES`.

The CHIP-8 gameplay view does not render through normal LVGL widgets for the emulator framebuffer. It writes scaled
`64x32` CHIP-8 rows directly with `ST7735_WritePixels()` at `2x` scale and keeps LVGL for surrounding labels/navigation.

## Application Flow

`Core/Src/main.cpp` is still CubeMX-shaped, but the application runtime is intentionally concentrated in `App_Init()`
and
`App_Task()`:

| Function     | Responsibilities                                                                                             |
|--------------|--------------------------------------------------------------------------------------------------------------|
| `App_Init()` | Initializes input, audio, settings, display/theme, main menu, and CHIP-8 UI state                            |
| `App_Task()` | Polls input/settings, dispatches current screen, services ROM upload when active, and calls `Display_Task()` |

Current main menu items:

| Item             | Behavior                                                                  |
|------------------|---------------------------------------------------------------------------|
| `Play`           | Opens the emulator menu: CHIP-8, SUPER-CHIP, ZX Spectrum 48K              |
| `USB ROM Upload` | Starts USB CDC upload mode and writes/verifies ROM pack in external flash |
| `Saves`          | Present in the menu but reserved for flash-backed state                   |
| `Settings`       | Volume setting persisted in W25Q128                                       |

Avoid putting long-running work directly in UI callbacks. Use the existing pending-action pattern in `app.cpp` when a
screen transition destroys/rebuilds LVGL objects.

## Input Notes

`Core/Src/input.c` manually configures GPIO pull-ups and treats all controls as active-low.

| Item                  | Value                 |
|-----------------------|-----------------------|
| Debounce              | `20 ms`               |
| Repeat delay          | `350 ms`              |
| Repeat period         | `90 ms`               |
| Repeatable buttons    | Up, Down, Left, Right |
| Action queue capacity | `64` entries          |

`Input_Tick1ms()` is called from `SysTick_Handler()`. Keep it short and deterministic; do not add heavy work,
allocation,
display calls, flash writes, or USB work inside the tick path.

## Audio Notes

`Core/Src/audio.c` drives PA8 as TIM1 channel 1 PWM and uses TIM5 as an `8 kHz` sample interrupt. PB2 controls the
PAM8302
shutdown pin and is driven high during initialization.

| Item            | Value                           |
|-----------------|---------------------------------|
| Sample rate     | `8000 Hz`                       |
| PWM top         | `255`                           |
| PWM center      | `128`                           |
| Volume range    | `0..100`                        |
| Built-in sounds | Navigation, select, back, reset |
| Built-in music  | Boot theme                      |

Do not call blocking HAL APIs or flash/USB routines from `Audio_TIM5_IRQHandler()`. It is a sample mixer ISR, not a
general-purpose task hook.

## External Flash Layout

The W25Q128 is `16 MiB` and is manually driven over SPI3 in `Core/Src/w25q128.c`.

| Region         | Offset     | Size            | Purpose                                                      |
|----------------|------------|-----------------|--------------------------------------------------------------|
| State/settings | `0x000000` | `1 MiB`         | Reserved state area; settings currently use the first sector |
| ROM pack       | `0x100000` | remaining flash | RPRP multi-system ROM-pack image                             |

Settings use a tiny append-only record log in the first `4 KiB` sector:

| Setting     | Notes                                                  |
|-------------|--------------------------------------------------------|
| Volume      | Defaults to `50`, stored as validated records with CRC |
| Save timing | Delayed by `750 ms`; retry delay is `1000 ms`          |

When adding save states later, do not trample `FLASH_LAYOUT_STATE_OFFSET` sector 0 unless the settings layout is
migrated
on purpose.

## CHIP-8 And ROM Pack Notes

The CHIP-8 core uses the standard `4096` byte memory model, `0x200` ROM start, `64x32` display, and `16` keys.

| Item                         | Value                                                   |
|------------------------------|---------------------------------------------------------|
| Max ROMs exposed by firmware | Shared ROM browser window over RPRP entries             |
| Max ROM size                 | `4096 - 0x200` bytes                                    |
| ROM-pack format magic        | `RPRP`                                                  |
| ROM-pack version             | `2`                                                     |
| ROM-pack header size         | `64` bytes                                              |
| ROM-pack entry size          | `72` bytes                                              |

The Python packer expects ROMs grouped by emulator folder, currently `roms/chip8/`, uses the `RPRP` format, stores the
system id in each entry, and aligns ROM data to `16` bytes. If the C structs or parser rules change, update both
`Core/Src/rompack.c` and `tools/pack_rompack.py` together.

To add another emulator, keep the shared layers shared instead of cloning CHIP-8 screens:

| Step                       | Location                                                              |
|----------------------------|-----------------------------------------------------------------------|
| Add a serialized system id | `Core/Inc/rompack.h` and `tools/pack_rompack.py` `SYSTEMS`            |
| Add source ROM folder      | `roms/<system>/`                                                      |
| Add runtime/UI driver      | New runtime files under `Core/Src` / `Core/Inc`                       |
| Register menu entry        | `Core/Src/emulators.cpp`                                              |
| Reuse ROM list             | `Core/Src/emulator_browser.cpp` through the runtime's `showRomList()` |

The CHIP-8 screen maps physical controls onto CHIP-8 keypad values as follows:

| Physical control | CHIP-8 key |
|------------------|------------|
| Up               | `0x2`      |
| Left             | `0x4`      |
| Right            | `0x6`      |
| Down             | `0x8`      |
| Center           | `0x5`      |
| A                | `0x7`      |
| B                | `0x9`      |
| X                | `0xE`      |
| Y                | `0xF`      |

Exit from gameplay is currently `B + Center` held for about `900 ms`.

## USB ROM Upload Notes

The USB upload path is active only on the upload screen. `RomUpload_Start()` initializes USB FS CDC, `RomUpload_Task()`
services protocol state, and `RomUpload_Stop()` shuts the mode down when leaving the screen.

| Protocol item     | Value                                     |
|-------------------|-------------------------------------------|
| Upload magic      | `C8UP`                                    |
| Header size       | `20` bytes                                |
| RX ring           | `8192` bytes                              |
| Max write payload | `4096` bytes                              |
| Verify chunk      | `512` bytes                               |
| Commands          | `HELLO`, `BEGIN`, `WRITE`, `END`, `ABORT` |

The protocol erases the ROM-pack flash region, writes incoming chunks, then verifies CRC. Keep the firmware protocol and
`tools/flash_rompack_usb.py` in lockstep; changing one side alone is asking for a very avoidable failure.

### LVGL Render Heap Debug Notes

Do not assume a crash during active UI work is a leak. For LVGL renderer issues, distinguish:

| Symptom                                                                                | Likely meaning                                |
|----------------------------------------------------------------------------------------|-----------------------------------------------|
| `mem_free` / `mem_biggest` fall after completed frames                                 | Real leak or retained object/text allocations |
| `frag_pct` rises while `mem_biggest` shrinks                                           | Heap fragmentation                            |
| `mem_free` returns after `Display_Task()` but `mem_max_used` climbs near `LV_MEM_SIZE` | Temporary render peak                         |
| `lv_mem_test()` fails or object pointers become impossible addresses                   | Heap corruption or use-after-free             |

Known project-specific LVGL issue: the USB ROM upload progress bar previously crashed around `69-70%` because
`LV_PART_MAIN` radius was `2` while `LV_PART_INDICATOR` radius was `1`. LVGL treated that as a clipped rounded indicator
case and used a temporary ARGB layer/mask path, pushing `mem_max_used` close to the `24 KiB` LVGL heap ceiling. Keep the
progress bar radii matched unless you verify render heap behavior again:

```cpp
lv_obj_set_style_radius(o, 2, LV_PART_MAIN);
lv_obj_set_style_radius(o, 2, LV_PART_INDICATOR);
```

When diagnosing these bugs, prefer a RAM breadcrumb with `lv_mem_monitor()` history around `Display_Task()` /
`lv_timer_handler()`. Use the matching `.elf` for the flashed artifact; if `Debug.hex` is flashed, decode with
`build/Debug/stm32-proj.elf`, not the release ELF.

## Coding Guidelines

| Area        | Rule                                                                                                |
|-------------|-----------------------------------------------------------------------------------------------------|
| Language    | Use C11-compatible C for application code                                                           |
| C++         | `Core/Src/main.cpp` is CubeMX-generated C++ entry code; keep custom logic inside `USER CODE` blocks |
| HAL usage   | Prefer HAL APIs already used by generated code                                                      |
| Interrupts  | Keep interrupt handlers short; move work into application code where possible                       |
| Memory      | Be conservative with stack and heap; current `.ioc` values are `0x400` stack and `0x200` heap       |
| Includes    | Prefer project headers in `Core/Inc` and avoid deep relative include paths                          |
| Vendor code | Treat `Drivers/` as third-party code                                                                |

## Verification Checklist

Before considering a change complete, run the relevant build:

```sh
cmake --preset Debug
cmake --build --preset Debug
```

For release-sensitive changes, also run:

```sh
cmake --preset Release
cmake --build --preset Release
```

Check linker memory output after builds because the toolchain file enables:

```text
-Wl,--print-memory-usage
```

After display, LVGL, GPIO, or SPI changes, build both presets and, when hardware behavior matters, flash
`build/Release/stm32-proj.hex` through ST-Link/STM32CubeProgrammer.

When debugging display color output, treat the flashed artifact as correct by default. Focus first on color format,
byte order, controller initialization, GPIO/SPI configuration, and the LVGL flush path.

## Agent Notes

- Read `Core/Inc/board_pins.h` and `../../docs/pinout.md` before changing any hardware-facing code.
- Read `stm32-proj.ioc` before changing peripheral, clock, pin, DMA, or NVIC behavior.
- Preserve `USER CODE` regions in CubeMX-generated files.
- Keep edits narrowly scoped; embedded projects punish casual churn.
- If adding new application modules, prefer new files under `Core/Src` and `Core/Inc`, then wire them through the root
  `CMakeLists.txt`.
- If CubeMX regeneration is expected, place custom logic where regeneration will not erase it.
- The current committed baseline is already beyond display bring-up and includes RetroPort app flow, CHIP-8, USB upload,
  W25Q128 storage, input, audio, and persisted settings. Do not treat LVGL/ST7735 as the only application layer anymore.
